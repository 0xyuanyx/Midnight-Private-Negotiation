## 2. 목표 제품

### 2.1 핵심 가치

**거래 당사자가 사전에 고정한 비공개 한도 안에서 합의를 확정하고, 외부에서는 그 조건이 충족됐음을 검증할 수 있는 B2B 협상 시스템.**

기업 승인자 연동 이후의 확장 목표는 “회사가 승인한 비공개 한도 안에서 자동 협상을 확정하는 시스템”이다. 현재 사용자가 직접 입력한 한도와 회사가 인증한 한도를 혼동하지 않는다.

고객이 얻을 것으로 기대하는 가치는 다음 세 가지이며 아직 고객 검증 전 가설이다.

1. 상대방과 플랫폼에 불필요한 예산·원가 관련 정보를 제공하지 않는다.
2. 협상을 위임하더라도 사전에 설정한 조건을 어기는 확정을 막는다.
3. 한도나 최종 거래가를 대중에게 공개하지 않고 합의 확정과 조건 준수의 검증 근거를 남긴다.

### 2.2 초기 고객과 범위

- 가설 고객: 반복 납품 계약을 협의하는 구매 담당자와 공급사 영업 담당자.
- 검증 대상 업무: 단일 거래 금액에 대한 사전 한도 설정 → 협상 → 가격 합의 확정.
- 현재 예시인 하도급 부품은 제품 맥락이다. 실제 기업 도입이나 법률 준수를 입증한 사례가 아니다.
- “단가”라고 표현하려면 금액의 단위가 품목당 가격인지, 납품 묶음의 총액인지 명시해야 한다. 1억 원 데모 값만으로 단위가 설명되지 않는다. 품목·수량·통화·세금 포함 여부의 바인딩은 후속 계약 조건 설계에 포함한다.
- 납품, 검수, 자금 이체, 세금계산서, 법적 계약 효력은 현재 보장 범위 밖이다.

### 2.3 Midnight를 쓰는 이유와 대안

암호화 메시지와 중앙 서버만으로도 비공개 협상을 구현할 수 있다. Midnight를 쓰는 추가 이유는 여러 당사자가 같은 운영자의 판단에만 의존하지 않고, 고정된 비공개 조건에 맞는 상태 전이를 검증하기 위해서다. 이 필요가 고객에게 없다면 중앙 서비스가 더 단순할 수 있다.

| 접근 | 장점 | 제약 | 현재 판단 |
|---|---|---|---|
| 중앙 서버가 양측 조건을 보관·판정 | 구현과 복구가 단순 | 운영자를 신뢰해야 함 | 고객 비교 대상 |
| 역할별 로컬 판정 + Midnight commitment·증명 | 한도 원문 없이 조건 준수와 동일한 합의를 검증 | 증명 지연, 키 관리, 출력 추론 문제 | 권장 주 경로 |
| MPC 등으로 한도 비교·가격 결정을 공동 계산 | 중간 제안의 노출 자체를 줄일 가능성 | 새 프로토콜·출력 정책·추가 검증 필요 | 장기 연구 후보 |

일반적인 협상도 한도를 직접 밝히지 않는다. 따라서 “숨길 수 있다”만으로 차별화하지 않고, 위임된 결정의 제한과 검증 가능성이 실제 업무에 필요한지 확인한다.

### 4.1 누구에게 무엇을 숨기는가

아래는 목표 구조다. 현재 단일 Controller 데모가 이미 이 분리를 만족한다는 뜻은 아니다.

거래 상대방은 최종 금액을 알아야 거래를 이행할 수 있다. “최종가 비공개”는 거래 당사자에게도 숨긴다는 뜻이 아니라 공개 원장과 불필요한 제3자에게 공개하지 않는다는 뜻이다.

### 4.2 증명 서버도 신뢰 경계에 포함

현재 역할별 전용 proof server(`midnightntwrk/proof-server:8.0.3` 컨테이너 2개)를 사용한다. `httpClientProofProvider`가 `/prove`로 보내는 payload에는 회로의 private witness 값(`ProofPreimage.private_transcript`)이 포함된다(Midnight Expert 소스 조사로 확인). 따라서 네트워크로 보내는 증명 요청·서버의 메모리·로그·디스크를 점검해야 한다. 당사자가 통제하는 로컬 증명과 외부 운영 증명 서비스를 동일한 보안 수준으로 설명하지 않는다.

### 4.3 공개 메타데이터

가격을 숨겨도 거래 존재, 시점, 상태 변화, 계약 주소, 공개 역할 키와 호출 관계 등에서 정보가 드러날 수 있다. 계약 호출 트랜잭션에는 계약 주소와 호출된 회로 이름(entry point)이 평문으로 들어간다. 예를 들어 `cancelAsBuyer`·`cancelAsSeller` 호출만으로 어느 쪽이 취소했는지 공개된다. 회로 이름과 공개 상태 변화의 설계도 공개 메타데이터 검토 대상이다. 거래마다 새 키를 쓰더라도 다른 식별자나 자금 흐름에 의한 연결 가능성이 자동으로 사라지지는 않는다. 익명 거래나 관계 비공개를 보장하지 않는다.

### 4.4 보호 범위 밖

상대방의 화면 캡처, 자체 로그, 이미 전달된 데이터 복제, 감염된 당사자 기기, 외부 AI 사업자의 보관, 감사자가 이미 받은 정보의 재배포는 앱의 로컬 삭제로 통제할 수 없다. 공모한 양 당사자가 거짓 거래를 합의하는 것도 한도 준수 증명만으로 막지 못한다.

## 5. 최종 금액을 공개하지 않는 온체인 구조

### 5.1 공개 원장과 오프체인의 책임

현재 계약의 공개 ledger 필드는 `dealId`, `buyerKey`, `sellerKey`, `buyerCommitment`, `sellerCommitment`, `priceCommitment`, `finalPrice`, `status`다. 목표 구조의 공개 원장에는 거래 식별자, 권한 확인용 공개값, 구매자·판매자 한도 commitment, 합의 가격 commitment, 거래 상태를 남기는 방향을 검토한다. 합의 가격은 당사자의 private state와 암호화된 최종 합의 증빙에 보관한다.

ZK 증명은 트랜잭션(`ContractCall.proof`)에 실려 검증 과정에서 쓰이며 계약 ledger 상태에는 저장되지 않는다. 증명을 별도 ledger 필드에 중복 저장하는 설계를 뜻하지 않는다. commitment는 암호화 파일이 아니므로 원문과 opening을 잃으면 commitment에서 복구할 수 없다.

### 5.2 필요한 논리 제약

다음은 구현 문법이 아닌 목표 조건이다. `B`는 구매자 한도, `S`는 판매자 한도, `P`는 양측 합의 가격이다.

```text
거래에 고정된 구매자 권한 검증
거래에 고정된 판매자 권한 검증
C_B = Commit(거래·역할·권한 문맥, B, r_B)
C_S = Commit(거래·역할·권한 문맥, S, r_S)
C_P = Commit(거래·가격·버전 문맥, P, r_P)
구매자 승인: C_B의 opening 일치 AND P <= B AND C_P 생성
판매자 확정: C_S의 opening 일치 AND S <= P AND 동일 C_P의 opening 일치
확정 결과: 상태 갱신, P 원문 공개 없음
```

구매자와 판매자가 각자 자신의 비밀만으로 같은 `C_P`를 매개로 검증하도록 한다. 현재 계약도 이 구조다. 회로 안의 `price <= maxPrice`, `minPrice <= price` 비교와 `C_P` 일치 검사는 성공 여부 외의 공개 값을 만들지 않는다. 한 회로에 양쪽 비밀 한도를 모두 모으는 것을 기본 전제로 삼지 않는다. 가격은 양수이고 통화·단위·허용 범위를 충족해야 한다. `Uint64`로 표현 가능하다는 사실만으로 업무상 유효한 가격이라는 뜻은 아니다.

### 5.3 상태 전이와 취소

현재 `WAITING_SELLER → OPEN → AUTHORIZED → SETTLED` 구조는 활용할 수 있다. `AUTHORIZED`는 구매자 승인 단계이며 최종 합의 확정과 구분한다. 미확정 단계의 취소, 승인 후 상대 오프라인, 중복 확정, 체인 실패·재시작을 정의해야 한다.

`CANCELLED`는 이번 거래가 확정되지 않았다는 상태다. `B < S`를 증명하는 상태가 아니다. 한쪽이 거부하거나 정해진 시도 횟수에서 합의가 안 된 경우도 포함될 수 있다. 합의 보장, 최적 가격, 공정한 가격 배분은 별도의 프로토콜 성질이다.

### 5.4 현재 계약을 수정할 때 함께 바꿀 부분

- `negotiation.compact`의 공개 `finalPrice` 필드·쓰기와 관련 스키마를 검토한다. 화면에서 숫자만 감추는 것은 해결책이 아니다. Midnight Expert 검증에서 `finalPrice` 필드와 `settle`의 `finalPrice = disclose(price)`를 제거한 사본이 compiler `0.31.1`로 컴파일되고, 로컬 runtime `0.16.0` 실행에서 가격·한도가 ledger, public transcript, 증명을 뺀 트랜잭션 바이트 어디에도 나오지 않음을 확인했다. 원본 계약은 `settle`에서 세 곳 모두에 가격을 남긴다. 실제 증명 생성·devnet 제출은 하지 않았으므로 단계 B 완료 기준을 대체하지 않는다.
- 두 한도의 commitment 검증, 같은 가격 opening 검증, 역할 권한과 상태 검사를 유지한다.
- Seller가 자신이 수락한 오프체인 가격과 Buyer가 보내온 opening을 대조하는 검사를 유지한다. commitment가 맞는 것과 사용자가 원한 합의인 것은 다른 검증이다.
- 생성된 bindings, adapter, Observer, IPC 이벤트, 브라우저 표시 정책, 테스트의 가격 공개 전제를 함께 수정한다.
- 당사자 전용 최종 가격 이벤트를 공개 WebSocket broadcast로 보내지 않는다. 현재 3패널 데모는 별도 신뢰 경계로 표시한다.
- 이미 체인에 공개한 구버전 금액은 지울 수 없다. 새 버전 계약·배포와 기존 거래 기록을 구분한다. 기존 상태를 자동 마이그레이션할 수 있다고 가정하지 않는다.

### 5.5 commitment 선택과 버전

현재 코드는 거래 ID·역할 도메인·키·금액·32바이트 난수를 조합한 `persistentHash`를 사용한다. 금액만 해시한 구조가 아니므로 `persistentHash`라는 이름만으로 무조건 취약하다고 결론내리지 않는다. 난수 생성·비밀 유지·재사용 금지와 직렬화 일치를 검증한다.

가격 commitment의 은닉성은 `priceRandomness`가 비밀이고 추측 불가능하다는 전제에 의존한다. 난수가 유출되면 가격 후보 범위가 좁아 전수 대입으로 가격을 찾을 수 있다.

새 구조에서는 표준 `persistentCommit` 사용도 비교한다. compiler `0.31.1`에서 `persistentCommit<T>(value: T, rand: Bytes<32>): Bytes<32>`가 존재하고, runtime `0.16.0`의 `persistentCommit`과 회로 계산 결과가 일치함을 실행으로 확인했다. 컴파일러는 commit 계열 결과를 입력 보호에 충분한 값으로 취급해 `disclose()` 없이 ledger에 쓸 수 있게 하고, `persistentHash` 결과는 witness에서 파생되면 `disclose()`를 요구한다. 이것은 컴파일러의 공개 분석 규칙이며, 현재처럼 32바이트 난수를 포함한 `persistentHash`가 암호학적으로 은닉되지 않는다는 뜻은 아니다. 변경 시 오프체인 계산과 회로 계산, 타입 인코딩, 도메인 분리, 과거 commitment 호환성을 함께 다룬다. 함수명을 교체하는 것만으로 보안이 완성되지 않는다. 공식 [표준 라이브러리](https://docs.midnight.network/compact/standard-library)와 [API](https://docs.midnight.network/compact/standard-library/exports)를 확인하되, 실제 계약 변경 후에도 고정 compiler `0.31.1`·runtime `0.16.0`에서 컴파일·실행해야 한다.

## 6. 중간 기록 폐기와 최종 증빙 보존

### 6.1 기본 원칙

**불필요한 기록을 처음부터 만들지 않고, 필요한 임시 기록은 수명을 제한하며, 최종 합의 증빙은 별도의 암호화 보관 대상으로 관리한다.**

프로세스 종료, 화면 초기화, DB 레코드 삭제는 동일한 보장이 아니다. JavaScript의 문자열·BigInt 복사본, GC, OS swap, SSD·백업의 잔여 데이터까지 완전 삭제했다고 주장하지 않는다. 키 폐기를 이용한 암호학적 삭제도 키 사본·백업을 모두 통제한다는 조건이 필요하다.

### 6.2 보관 정책 초안

| 종류 | 필요한 동안의 처리 | 정상 종료 후 목표 | 예외·검증 사항 |
|---|---|---|---|
| AI 내부 후보·guard 탈락 결과 | 역할 메모리에서 판단에만 사용 | 가능한 즉시 참조 해제, 영속 로그 금지 | 에러 리포트·추적 도구에 포함 금지 |
| 주고받은 협상 제안 | 협상·중복 방지에 필요한 최소 상태 | 완료·취소 후 임시 상태 정리 | 상대가 보관한 사본은 삭제 보장 불가 |
| Relay 암호문·큐 | 전달·한정된 재시도 동안 | 전달 완료 또는 설정된 TTL 만료 시 정리 | 서버 종료·재시작·오류 경로 포함 |
| 한도와 한도 opening | 증명·재시도에 필요한 기간 | 확정 확인 후 정책에 따라 암호화 보관 또는 폐기 | 후속 한도 공개·재증명 필요성부터 결정 |
| 임시 세션 키 | 해당 세션 통신 동안 | 세션 종료 시 폐기 | 지갑 장기키와 분리, 백업·덤프 점검 |
| 가격과 가격 opening | 합의와 증빙 생성 동안 | 최종 합의 보관소에 암호화 보존 | 삭제하면 나중에 가격 commitment를 열 수 없음 |
| 최종 합의 문서·승인 근거 | 거래 확정 시 생성 | 당사자별 접근 제어와 암호화 보관 | 고객 계약·분쟁 대응 요건에 따라 기간 결정 |
| 공개 원장 | 공개 검증에 필요한 최소값 | 계속 공개된 것으로 취급 | 삭제·TTL 보장 불가 |
| 외부 AI 요청 | 정책이 허용한 입력만 전송 | 사업자의 실제 보관 정책에 따름 | 로컬 삭제로 원격 삭제를 보장하지 않음 |

TTL·보관 기간의 숫자는 아직 확정하지 않았다. 중간 기록의 최대 수명은 운영상 재시도 시간에서, 최종 증빙의 기간은 고객 요구와 관련 보관 의무 검토에서 정한다. 임의의 날짜를 법적 의무로 문서화하지 않는다.

### 6.3 삭제 시점과 복구 순서

1. 합의가 체인에 확정됐는지 현재 네트워크의 확정성 기준으로 확인한다.
2. 각 당사자가 최종 증빙을 암호화 저장했고 재검증할 수 있는지 확인한다.
3. 더 이상 증명·재시도에 필요 없는 중간 상태와 세션 키를 정리한다.
4. 종료 상태와 정리 작업의 성공 여부만 민감값 없이 기록한다.
5. 비정상 종료 시 재시작 정리 작업이 만료된 세션을 처리한다.

체인 결과가 불확실한데 모든 witness를 먼저 지우면 복구할 수 없다. 반대로 복구를 이유로 중간 기록을 무기한 보관하지 않도록 만료·재시도 정책을 둔다. 두 당사자의 보관 완료를 기다리는 정책에는 상대 미응답 시 종료 조건도 필요하다.

### 6.4 현재 코드의 별도 점검 대상

`packages/midnight-adapter/src/index.ts`는 `levelPrivateStateProvider`를 사용한다. DB 경로·보관·삭제 API, 역할별 `agreedPrice`와 `priceOpening` 잔존 여부, proof server 로그를 실제 실행으로 조사해야 한다. 현재 “모든 중간 내역이 자동 폐기된다”는 완료 주장은 할 수 없다.

동일 파일에서 storage password를 공개키 계열 `accountId`로부터 결정적으로 만드는 구성이 보인다. 디스크를 얻은 공격자에 대한 비밀 기반 암호화 경계로 신뢰해서는 안 된다. 실제 저장 형식·공격 재현은 이번 문서 작업에서 하지 않았으며, 제품화 전 OS 보안 저장소 또는 별도 비밀 기반 키 관리로 교체·검증할 대상이다.

기존 사용자의 기록을 자동으로 지우는 마이그레이션은 이 문서가 승인하지 않는다. 폐기 정책은 새 세션부터 적용하는 방식과 기존 기록 정리 절차를 구분한다.

## 7. 선택 공개와 최종 합의 증빙

목표 증빙 패키지는 거래 ID·네트워크·계약 주소·회로/정책 버전, 합의 금액·통화·단위, 가격 commitment와 opening 난수, 최종 체인 상태 참조, 양측의 합의 확인 근거를 포함한다. 회사 승인자 인증이 구현되기 전에는 해당 사실을 포함했다고 주장하지 않는다.

권한 있는 감사자는 받은 금액·opening으로 commitment를 다시 계산하고, 해당 거래의 확정 상태와 비교할 수 있다. 이 공개는 오프체인 전달로 설계할 수 있으며 공개 체인에 금액을 다시 올릴 필요는 없다. 추가적인 “가격이 특정 범위 안이다” 같은 조건만 공개하는 ZK 회로는 별도 기능이다.

- 가격 opening을 공개해도 상대방의 한도 opening이나 비밀키를 함께 넘기지 않는다.
- 증빙만 보관하고 가격 opening을 지우면 commitment 대조가 불가능해질 수 있다.
- 두 당사자가 이미 알고 있는 최종 가격을 상대방이 다른 사람에게 말하지 못하도록 암호학적으로 강제할 수는 없다.
- 감사 권한 회수는 향후 접근을 제한할 수 있지만 이미 전달된 파일을 회수하지는 못한다.
- 암호학적 무결성 증거와 법적 효력은 별개다. 법적 집행 가능성은 미검증이다.

## 8. 협상 전략과 추론 누출

### 8.1 최우선으로 보완할 현재 문제

현재 fallback은 공개된 라운드 공식으로 비밀 한도의 비율을 계산해 외부 제안으로 사용한다. 앞선 평가에서 Buyer 한도 90,000,000원, 공개 기준가 100,000,000원, 1라운드 제안 81,000,000원을 재현했다. 해당 fallback 경로를 알면 한도를 90,000,000~90,000,277원으로 좁힐 수 있다.

문제의 위치는 `agent-core/src/index.ts`의 `localTargetPrice`, `generateLocalFallbackCandidate`이며, 상대 런타임과 AI의 `currentOffer`에 이 정보가 전달될 수 있다. 자동 폐기·Relay 암호화·최종가 비공개는 이 추론 경로의 대체 해결책이 아니다.

### 8.2 권장 전략

- 외부 제안은 공개 기준가와 사전에 합의한 공개 규칙을 기준으로 만든다.
- 비공개 한도는 로컬 정책 검사와 회로 증명에 쓴다.
- 한도에 맞춰 공개 제안을 잘라내거나 clamp한 값을 전송하면 한도를 그대로 드러낼 수 있으므로 피한다.
- 허용 후보가 없을 때 한도의 일정 비율을 전송하는 fallback을 금지한다.
- 무작위 잡음만 추가하고 안전하다고 주장하지 않는다. 반복 관측으로 평균·경계를 추정할 수 있다.
- 제한된 시도 횟수, 거래별 재협상 규칙, 상대 인증과 반복 질의 억제를 함께 검토한다. 4자리 코드만 바꾸면 제한을 우회할 수 있는 설계는 충분하지 않다.

### 8.3 정직하게 남겨야 할 한계

수락·거절만으로도 한도 범위가 줄어들 수 있고, 한도에 의존해 후보를 선택하는 과정 자체에도 정보가 있다. 거래 당사자는 합의된 `P`로부터 최소한 `S <= P <= B`가 성립한다는 사실을 알게 된다. 공개 규칙 제안으로 바꿨다는 이유만으로 완전한 추론 방지가 달성되지는 않는다.

전체 한도 비밀성을 엄밀하게 보장하려면 출력 누출을 정의한 별도 협상 프로토콜 검토가 필요하다. 테스트는 알려진 공격 회귀와 추정 성능을 확인하는 수단이며, 모든 공격이 불가능하다는 수학적 증명이 아니다.

## 9. AI 사용 정책

AI는 후보를 제안한다. 로컬 guard가 전송·수락을 제한하고 계약이 확정 조건을 검증한다. AI가 한도 정책이나 거래 확정 권한을 대체하지 않는다.

2026-09-23 단계 A 이후 코드 기준: 첫 번째 허용 후보가 선택되므로 AI는 안전 조건을 바꾸지 못하지만, 허용 범위 안에서 행동(수락 대신 역제안을 먼저 보내는 순서, 합의 시점, 허용 범위 안 금액)을 바꿀 수 있다. mock 생성기는 공개 사다리 가격만 낸다. 발표의 중심은 AI 협상 성능이 아니라 비공개 조건을 지키는 자동 협상과 검증이다.

최종 가격의 외부 AI 비공개까지 목표로 삼는다면 현재 `currentOffer` 전송 방식은 재설계해야 한다. AI가 본 제안이 그대로 최종 합의가 될 수 있으므로 “완료 후 최종 가격을 따로 보내지 않는다”만으로 비공개가 되지 않는다.

| 모드 | 외부 모델이 받는 정보 | 적합한 설명 |
|---|---|---|
| 로컬 결정론적 협상 | 없음 | 외부 AI 전송 없는 기준 구현 |
| 공개 맥락만 쓰는 외부 AI | 당사자가 허용한 기준가·규칙 등, 개별 제안 금액 제외 | 제한된 후보/전략 지원, 협상 성능 별도 평가 |
| 현재 제안까지 보내는 외부 AI | 협상 가격 일부 포함 | 한도 원문은 미전송하나 제안 가격은 외부 처리 |
| 당사자가 통제하는 로컬 모델 | 당사자 경계 안에서 허용된 입력 | 외부 전송 경로·로그·실행 환경 확인 필요 |

권장 기본선은 외부 모델 없이도 동작하는 검증 가능한 협상이며, AI의 추가 효과가 측정될 때 확장한다. 실제 입력으로 받은 거래 정보를 공개 정보라고 자동 분류하지 않는다. `store: false` 같은 단일 API 설정을 전체 무보관 보장으로 해석하지 않으며 실제 사업자 정책을 별도 확인한다.

합성 데이터로 합의율, 한도 위반 확정 0건, 불필요한 결렬, 라운드, 지연, 비용, fallback 비중을 비교한다. 실거래의 guard 거절 횟수·모델 선택 여부를 상대방에게 실시간 노출하지 않는다. 재현용 명시적 mock/실모델 모드 고지와 비밀 추론을 돕는 telemetry 공개는 구분한다.

## 10. 단계별 개발 순서와 완료 기준

### 단계 A — 기존 제출물의 핵심 주장과 알려진 문제 보완

> 2026-09-23 구현 완료(`dc207eb`). 제안 가격은 공개 기준가와 라운드로만 계산하는 공개 사다리에서 나오고, 알려진 역산 사례의 회귀 테스트를 추가했다. 남는 누출은 수락·중단 시점의 2%p 구간이다.

범위: 한도 비율 fallback 제거, 추론 위협 명세, 입력·가격 단위 일치, CANCELLED·SETTLED 설명 정정, 현재 모드 고지.

완료 기준: 알려진 역산 사례가 더 이상 해당 경로로 재현되지 않음, 한도 위반 확정 거절, 기존 성공·결렬·제3자 거절 회귀 통과, API 요청·Relay·공개 이벤트 경계 검증. 아직 남는 수락/거절 추론을 문서화한다.

### 단계 B — 최종가 비공개 확정의 세로 방향 구현

> 2026-09-23 구현 완료(`df9b157`). 로컬 체인에서 성공·결렬을 실행하고 Indexer 트랜잭션 7건의 원문과 계약 상태에 가격·한도 인코딩 값이 없음을 확인했다. 당사자의 최종 증빙은 기존 private state 저장소에 남으며, 별도 암호화 증빙 보관은 단계 C 범위다. mock provider 기준이며 실제 OpenAI 모드는 다시 실행하지 않았다.

범위: 계약 → adapter → 역할 런타임 → Observer → 화면/제출물까지 일관되게 전환하고, 당사자 최종 증빙 저장을 함께 구현한다.

완료 기준: 실제 체인 성공 후 ledger·공개 트랜잭션 데이터·Indexer·Observer·공개 이벤트에 최종 금액과 opening이 없음. 양측은 같은 금액을 확인하고 보관된 opening으로 공개 commitment를 검증 가능. 가격·난수 변조와 역할 위조가 거절됨.

UI에서 숨긴 것, 금액 문자열 단순 검색이 0건인 것만으로 통과하지 않는다. 인코딩된 값, 공개 출력, 오류, 저장 경로를 검사한다. 해당 변경이 끝나면 구버전의 최종가 공개 영상을 새 구조의 증거로 쓰지 않는다.

### 단계 C — 명시적인 보관·폐기·복구

> 2026-09-23 최소 구현 완료. 역할별 증빙 암호화 보관·재대조, 키체인 기반 저장소 키, 체인 확정·증빙 확인 뒤 private state 정리, 시작 시 복구, 앱 종료 후 증빙 확인 CLI. 증빙 쓰기 도중 종료 복구는 단위 테스트로만 확인했다.

범위: 임시 상태와 최종 증빙 저장소 분리, 세션 TTL, 정상·오류·재시작 정리, 로컬 키 관리.

완료 기준: 합성 표식 데이터로 통제하는 저장소의 잔존 경로를 확인하고, 삭제 실패·중단·재시작 시 재시도 동작 검증. 증빙 백업을 복원해 commitment 대조 가능. 상대 기기·외부 사업자·OS 복사본까지 삭제했다고 주장하지 않음.

### 단계 D — 실제 양측 사용자와 기업 승인

범위: 독립 클라이언트, 인증된 상대 연결, 역할별 전송 권한, 기업 승인자의 한도 commitment 인증.

완료 기준: 한쪽 사용자가 다른 쪽의 한도·private state에 접근하지 못함, Relay/운영자가 키 교환을 바꿔 중간자 역할을 하지 못하도록 상대 키와 거래 문맥을 인증, 승인 문서의 거래·버전·만료·취소 정책 검증.

기존 공개키 소유 증명은 실제 회사의 권한을 증명하지 않는다. 승인자를 연결하더라도 승인한 값의 원가 진실성까지 보장하지 않는다.

### 단계 E — 고객 검증에 따른 확장

실제 고객 요구에 따라 최종가 선택 공개, 다중 조건 협상, 원재료 연동 계산, 결제·에스크로를 개별 과제로 검토한다. 모든 기능을 동시에 추가하지 않는다. 실제 지급을 연결하면 금액·자금 흐름 노출과 실패 시 자산 안전을 다시 설계해야 한다.

## 13. 고객·사업 검증

우선 구매 담당자와 공급사 담당자 2~3명의 문제 탐색 인터뷰를 제안한다. 이는 시장 검증 완료가 아니다.

1. 최근 협상에서 실제로 공개한 정보와 공개하고 싶지 않았던 정보는 무엇인가?
2. 한도를 사전에 고정하면 업무에 도움이 되는가, 협상 유연성을 해치는가?
3. 최종 가격을 공개 원장에 올리는 방식을 허용하는가?
4. 누가 한도를 승인하며, 담당자가 이를 지켰다는 증거를 누가 필요로 하는가?
5. 몇 분의 처리 시간이 허용되는가? 줄이고 싶은 비용은 시간, 승인 업무, 정보 유출 중 무엇인가?
6. 분쟁 때 어떤 증빙을 얼마나 보관해야 하는가?
7. 외부 AI에 현재 제안을 보내도 되는가?

답변이 긍정적이어도 고객, 유료 계약, 도입 실적이라고 표현하지 않는다. B2B 구독·거래당 과금·검증 API는 수익모델 후보이며 아직 확정하지 않는다. 한도 사전 고정의 필요가 없거나 운영자 신뢰만으로 충분하다는 답변이 반복되면 제품 가설을 수정한다.

기존 제출 마감 기록은 2026-09-28 00:00 KST다. 앞선 평가에서 확인한 [대회 안내](https://www.risein.com/midnight/midnight-korea-hackathon-2026)는 로컬 devnet을 허용한다. 제출 직전 실제 공고·양식 변경을 재확인한다.

단계 A·B는 이번 제출 버전에 포함하기로 결정했고 코드·로컬 체인 검증을 완료했다. 제출 전 우선순위는 **새 버전의 데모 영상을 재녹화하고 링크를 반영하는 것**이다. 9월 18일 영상은 합의 가격이 공개되던 이전 버전을 보여주므로 새 버전의 증거로 사용할 수 없다. README·제출 양식·영상의 보장 범위를 대조하고, 현재 공개 사다리에도 수락·중단 시점의 추론 누출이 남는다는 점을 유지한다.

독립 클라이언트 전면 재구축, 기업 승인자 인증, 에스크로, 연동제 회로는 기본적으로 후속이다. 다만 고객용 독립성 보장이 없다는 사실은 명시한다.

영상은 문제 → 비공개 입력 → 핵심 상태 전이 → 거절/변조 방어 → 고객 가치·현재 한계 순으로 구성한다. 성공·결렬의 반복 입력을 줄이고 결과를 확대한다. Observer에 금액이 없는 장면과 당사자의 금액 확인·commitment 대조 장면을 함께 보여준다. 실제 입력값은 합성 시연 데이터임을 표시한다.

AI mock/실모델, 로컬 체인, 배속 구간, Controller 신뢰 경계는 계속 고지한다. 현재 `SETTLED`를 대금 지급 완료로 설명하지 않는다.

## 15. 수상 가능성과 평가 기준

2026-09-23 평가의 핵심은 기술 구현·재현성에 비해 프라이버시 주장과 고객 설득력이 약하다는 것이다. 경쟁력 있는 출품작 10~20팀을 가정한 이전 주관 추정은 현재 상위 3팀 15~30%, 핵심 문제 보완·검증과 고객 근거·영상 개선 후 35~50%였다. 실제 출품작·배점 기반 통계가 아니며 개선 후 숫자를 현재 확률로 쓰지 않는다.

최종가 비공개 하나를 추가하거나 기능 수를 늘렸다고 확률을 올려 평가하지 않는다. 다음 네 가지가 실제로 확인될 때 재평가한다.

- 핵심 프라이버시 주장이 코드와 실행 증거에 부합하는가?
- 일반 협상·중앙 서비스에 비해 필요한 이유가 고객 답변으로 뒷받침되는가?
- 제3자가 설치·실행·거절 사례를 재현할 수 있는가?
- 심사위원이 2분 안에 문제·가치·Midnight의 역할·한계를 이해할 수 있는가?

| Relay와 증명 서버의 운영 주체는? | 각 당사자가 신뢰할 경계를 명시, 외부 호스팅 시 재검토 |
| 거래 상태·역할 키까지 숨겨야 할까? | 초기 목표 밖, 고객의 관계 노출 요구가 확인되면 별도 설계 |
| 기업 승인자·감사자의 권한 회수는? | 조직 인증·만료·폐기·과거 승인 효력을 후속 명세로 결정 |

## 17. Midnight 스킬 적용과 검증 근거

### 17.1 초안 작성 시 참고한 스킬

초안은 Codex 로컬 스킬 `midnightskill`, `midnight-security`, `compact`, `why-midnight`(`~/.agents/skills/`)을 설계 보조 자료로 사용했다. 스킬은 실제 코드와 공식 문서보다 우선하는 기술적 사실의 근거로 취급하지 않았고, 일반 예제를 컴파일된 구현처럼 제시하지 않았다. 일부 스킬의 “회로 인자는 모두 공개”라는 요약은 아래 검증 결과와 맞지 않는다.

공식 [Explicit disclosure](https://docs.midnight.network/compact/reference/explicit-disclosure)는 비밀에서 파생된 값도 공개 검토 대상이며, `disclose()`가 공개 허용을 알리는 컴파일러 표식임을 설명한다. 공개 여부는 실제 ledger 쓰기·반환·다른 계약 전달 등 데이터 경로로 판단한다. 공식 문서는 exported circuit·constructor 인자도 witness data의 출처가 될 수 있다고 설명하며, 아래 실행 검증도 이와 일치한다. 현재 가격 입력은 witness 경로를 유지한다.

### 17.2 Midnight Expert 검증 기록 (2026-09-23)

Claude Code의 Midnight Expert 플러그인(`midnight-verify`)으로 문서의 Midnight·Compact 주장을 다시 확인했다. 실행 검증은 프로젝트 고정 버전 compiler `0.31.1`(`--skip-zk`)과 `@midnight-ntwrk/compact-runtime` `0.16.0`으로 별도 작업 공간에서 수행했으며 프로젝트 코드는 수정하지 않았다.

| 주장 | 결과 | 근거 |
|---|---|---|
| exported circuit·constructor 인자는 공개 분석에서 witness data로 취급되고, 공개 경로가 없으면 public transcript에 나오지 않음 | 확인 (실행) | `disclose()` 없는 ledger 쓰기 컴파일 거부, assert·해시 전용 인자는 prover 입력에만 존재 |
| `disclose()`는 값을 변환·암호화하지 않는 표식 | 확인 (실행) | ledger에 입력값이 그대로 저장됨 |
| `persistentCommit`이 `0.31.1` 표준 라이브러리와 runtime `0.16.0`에 존재하고 결과가 일치 | 확인 (실행 + 소스) | 회로·오프체인·pure circuit 결과 동일, commit은 `disclose()` 불요·hash는 필요 |
| `finalPrice` 제거 시 가격이 ledger·public transcript·트랜잭션에 없음 | 확인 (실행) | public transcript는 상태 읽기·쓰기, 키·거래 ID·commitment 읽기, `priceCommitment` 쓰기만 포함 |
| 증명은 트랜잭션에 실리고 계약 ledger 상태에 저장되지 않음 | 확인 (소스) | midnight-ledger `ContractCall`에 `proof`, `ContractState`에는 없음 |
| 계약 주소와 호출 회로 이름이 트랜잭션에 공개 | 확인 (소스) | `ContractCall.address`, `ContractCall.entry_point` 평문 필드 |
| proof server가 private witness 값을 받음 | 확인 (소스) | midnight-js `httpClientProofProvider` → `/prove` payload의 `ProofPreimage.private_transcript` |
| Buyer fallback 1라운드 제안 81,000,000원에서 한도를 90,000,000~90,000,277원으로 역산 가능 | 확인 (실행) | 빌드된 `localTargetPrice`로 경계값 재현 |
| 루트 테스트 47/47 | 확인 (실행) | `npm test` 재실행 |

한계: 실제 ZK 증명 생성, devnet 제출, Indexer 조회는 하지 않았다. 소스 조사는 최신 공개 저장소 기준이며 `0.31.1` 태그를 직접 읽지는 않았다(`0.31.0` 이후 해당 함수의 변경 기록은 없음). 따라서 위 결과는 단계 B의 설계 전제를 뒷받침할 뿐, 단계 B 완료 기준(실제 체인의 공개 데이터 검사)을 대체하지 않는다.
