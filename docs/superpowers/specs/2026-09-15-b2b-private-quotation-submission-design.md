# B2B 비공개 견적 협상 제출 설계

상태: 2026-09-17 구현 반영. 검증 결과는 `README.md`와 `docs/2026-09-09-review-reproducibility.md`를 확인한다. 2026-09-18에 제출 시나리오를 하도급 부품 납품 단가 협상으로 교체했다. 아래 GPU 서버 시나리오는 이력이며, 현재 결정은 `PROJECT_DIRECTION.md`를 따른다. 신뢰 경계·범위·완료 기준은 그대로 유효하다.

## 목표

기존 Private Negotiation DApp을 새 제품으로 확장하지 않고, Midnight Korea Hackathon 제출을 위해 메시지와 데모를 하나의 B2B 견적 시나리오에 맞춘다. 심사자가 Buyer·Seller의 예약 가격은 숨겨지고, 성립한 거래의 최종 가격만 Midnight에서 공개된다는 흐름을 짧게 확인할 수 있어야 한다.

## 고정된 제품 메시지

> 구매 담당자의 최대 승인 한도와 공급업체의 최저 수용가를 상대방·AI·Relay·공개 원장에 공개하지 않고, 양측 정책을 만족한 거래만 Midnight에서 검증한다. 거래가 성립하면 최종 합의 가격만 공개한다.

`플랫폼에 공개하지 않는다`는 표현을 사용하지 않는다. 현재 브라우저와 Demo Controller는 로컬 데모 신뢰 경계이며, Buyer·Seller 한도는 Controller를 통해 각 역할 런타임에 평문으로 전달된다. Controller는 한도를 보관하거나 표시하지 않지만, 전송 중에 취급한다.

AI는 공개된 상품 코드·기준가격·현재 제안·라운드와 역할 정보로 후보 가격을 만드는 교체 가능한 제안자다. 표의 품목·수량·납기는 발표용 정적 맥락이며 현재 AI 요청이나 계약 데이터에 포함되지 않는다. AI가 비공개 한도를 지키는 주체가 아니다. 각 역할의 로컬 PolicyGuard와 StrategyGuard가 후보를 검사하고, Midnight 계약이 성립한 거래에서 비공개 한도와 합의 가격의 관계를 검증한다.

## 첫 적용 시나리오

가상의 기업 구매 담당자와 GPU 서버 공급업체가 동일 규격 GPU 서버 10대의 견적을 협상한다.

| 구분 | 공개 여부 | 데모 값 |
|---|---|---|
| 품목 | 공개 | 동일 규격 GPU 서버 10대 |
| 기준가격 | 공개 | 100,000,000 KRW |
| 납기 | 공개 | 30일 |
| 구매자 최대 승인 한도 | 비공개 | 성공 데모 110,000,000 KRW |
| 판매자 최저 수용가 | 비공개 | 성공 데모 95,000,000 KRW |
| 최종 합의 가격 | 성립 시 공개 | 계약 `SETTLED` 뒤에만 표시 |

성공 값은 시연을 위한 고정 예시이며 실제 GPU 거래 가격이나 검증된 고객 데이터를 뜻하지 않는다. 결렬 데모는 구매자 최대 승인 한도 90,000,000 KRW와 판매자 최저 수용가 95,000,000 KRW를 사용한다.

## 범위

### 이번 제출에 포함

- Buyer·Seller·Observer로 구성된 기존 한 화면 3패널 콘솔
- GPU 서버 10대 B2B 견적이라는 정적 공개 맥락
- 기존 250 KRW 단위와 대칭형 비공개 양보 전략
- 성공, 한도 미중첩 결렬, 제3자 비밀키로 정산을 시도했을 때의 거절 검증
- README, 발표 스크립트, 최종 새 클론 검증

### 이번 제출에서 제외

- 실제로 독립된 Buyer·Seller 브라우저 또는 원격 클라이언트
- 다수 판매자 경매, 결제, 에스크로, 물류, 복수 상품 동시 협상
- 새 AI 공급자나 모델 교체
- 최종 가격까지 비공개인 B2B 거래 모델
- 실제 고객·시장 검증을 마친 제품이라는 주장

브라우저 탭을 나누는 것만으로는 독립 클라이언트가 되지 않는다. 현재 Controller는 한도를 전달하고 모든 정제 이벤트를 연결된 소켓에 broadcast하며, 브라우저 인스턴스별 session ID도 동일 상품 코드의 별도 브라우저를 자동으로 같은 협상방에 연결하지 않는다. 이 구조의 변경은 제출 범위 밖의 별도 아키텍처 작업이다.

## 화면과 카피

디자인 시스템의 3패널 터미널 레이아웃, 색상, 로그 정책을 유지한다. 새 카드, KPI, 사이드바, 대시보드를 만들지 않는다.

- 헤더 제목은 `GPU 서버 10대 · 비공개 B2B 견적 협상`으로 바꾼다.
- Buyer·Seller의 입력 라벨은 현재의 `구매자 최대 한도`, `판매자 최소 금액`을 유지한다.
- Observer에는 공개 계약 상태와 `OPEN`, `AUTHORIZED`, `SETTLED`만 보인다.
- 협상 중 제안 가격, 라운드, PolicyGuard·StrategyGuard 판단, 한도 원문은 어느 패널에도 보이지 않는다.
- 성공 뒤에만 최종 합의 가격을 표시한다. 결렬에서는 어떤 금액도 표시하지 않는다.

## 데모 흐름

### 1. 성공

Buyer와 Seller가 상품 코드 `4821`을 입력하고 각각 110,000,000 KRW와 95,000,000 KRW를 입력한다. 공개 기준가격을 바탕으로 AI 또는 mock provider가 후보를 만들고, 역할별 로컬 guard가 통과한 후보만 사용한다. Observer는 `OPEN`, `AUTHORIZED`, `SETTLED` 순서와 최종 가격만 본다.

### 2. 한도 미중첩 결렬

동일한 공개 조건에서 Buyer 90,000,000 KRW와 Seller 95,000,000 KRW를 입력한다. 증명·정산 단계 없이 `CANCELLED`로 끝나며, Observer와 상대방은 각자의 한도와 실패한 제안을 보지 못한다.

### 3. 무단 정산 거절

계약이 `AUTHORIZED`인 상태에서 Seller secret key가 아닌 제3자 secret key로 `settle` witness를 만들면 계약의 `publicKey(sellerSecretKey()) == sellerKey` 검사에서 거절되어야 한다. 이 경로는 UI에 별도 버튼을 만들지 않고 Compact 계약 테스트와 발표용 터미널 출력으로 보여준다.

## 완료 기준

- 공개 원격의 최종 커밋을 새로 클론해 `npm run bootstrap`, `npm test`, 웹 `npm ci`, 웹 `npm test`가 통과한다.
- 로컬 Midnight Devnet에서 성공 흐름의 Observer `SETTLED`가 확인된다.
- 미중첩 입력에서 proof와 settlement 이벤트가 발생하지 않고 `CANCELLED`가 확인된다.
- 제3자 secret key의 settlement 시도가 계약에서 거절되고, 이를 확인하는 회귀 테스트가 통과한다.
- README와 발표 문구가 이 문서의 신뢰 경계·최종 가격 공개 범위와 모순되지 않는다.
